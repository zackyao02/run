# PRD V1.10

## 1. 用户与问题

第一用户是已经读过一篇方法型知乎内容、准备真正照着做的人。具体用户与题材不预先固定，运行形态由文章结构决定。

现有文章解决“知道”，没有解决“照着做”。用户仍要反复翻找步骤、自己记住进度、判断遗漏，并承担 AI 改写后偏离原意的风险。把文章逐句做成待办也无效：那只是换皮清单，不会形成新的执行能力。

## 2. 一句话定位

**把知乎方法型知识，变成有原文依据、状态会迁移、能留下结果的 Run。**

## 3. 核心机制

```text
知乎官方来源自动读取 / 完整赛事模拟知识读取
→ AI 判断是否适合执行
→ AI 编译受限交互 Schema
→ Schema / Source Anchor / Safety 校验
→ 人工 Preview / Publish
→ 无 LLM 的稳定 Runtime
→ Session / Result Artifact
→ 用户可选 AI 结果解读
```

AI 的必要性不在“生成 JSON”，而在四个判断：什么能转成行动、哪种交互优于继续阅读、每个行动是否被原文支持、何时应当拒绝编译。只有具备至少两种程序原语的文章才可进入 Compiler：可观察状态、原文分支、确定性评估、反馈回路、可重复实验、可保留结果物。

## 3.1 七种程序模型

- 情境模拟器：有限情境选择改变声明的状态变量，并生成行动轨迹。
- 诊断路径图：原文条件分支定位当前节点，保留判断证据与缺口。
- 微型实验室：短时计时实践、观察记录与可重复实验结果。
- 规则压力测试器：本地输入运行白名单确定性规则，显示结构缺口。
- 行动编排器：原文规定的前置条件、解锁与补救路径形成可恢复地图。
- 对话排练器：文章明确话术逻辑形成有限状态对话，不用运行时 LLM。
- 参数沙盘：在文章声明的有限参数值之间切换，查看确定性状态改变。

这些是 Runtime 能力，不是发布数量要求；没有满足原文结构的真实 Source，就必须拒绝对应模型。

## 4. Hero

- 用户：已经读过一篇方法型知乎内容、准备真正照着做的人。
- Grammar：从 Inspect、Mission、Diagnose、Practice 中选择。
- Source 选择标准：完整知乎原文或完整赛事模拟知识、可执行、可完成、低风险、关键行动可锚定。真实完整正文可来自赛事详情接口，或当前 Access Secret 所属账号的知乎创作分析接口；模拟知识由受控预置内容提供，并在页面统一标识。
- Hero Moment：用户在一篇知识上点击“用一下”，输入自己的情况，直接运行由该文章编译出的程序，看到不同状态、下一步 Result 并回看原文证据。

Hero 的具体 Source 与 Grammar 由真实内容池确认，不把任何固定题材反过来强行套进产品。正文不由用户导入：系统只会自动读取赛事知识池，或当前授权账号自己发布的知乎内容。不能粘贴正文、上传文件、输入任意文章链接或抓取第三方网页。

## 5. P0 用户流程

1. 在发现页看到已发布 Run 卡片、知乎作者、来源和 Started / Completed。
2. 进入详情页了解用途、预计时间与来源。
3. 创建 Session，但此时不计 Started。
4. 第一次有效勾选或选择后计 Started。
5. 用户按文章编译出的交互进行操作，可随时查看原文证据。
6. 刷新或离开后能从上次进度恢复。
7. 满足后端 Completion Rule 后完成。
8. Result 先只汇总本次状态；用户可额外点击“AI 辅助解读”，让模型基于本次填写、确定性 Result 与相关原文片段提供解释。该输出必须与 Result 分区展示，不改变状态、路径、完成计数或原文依据。

## 6. P0 范围

### 内容

- 至少 1 个真实来源 Proof Run，另有 3–4 篇完整赛事模拟知识 Run；至少三种明显不同的体验。模拟知识必须统一标识，不能称作官方接口正文。
- 真实 Source 不预设题材；赛事模拟知识采用具体、高频、低风险的真实问题，确保正文中的条件能够形成可执行程序。
- 内容生产只允许受保护的自动 Source Provider：赛事知识池，或当前 Access Secret 所属账号的创作分析全文。发布文章后会自动出现在内部候选列表；不设置正文导入功能。

### Runtime

- P0 组件：intro、check、task、choice、result。
- 至少完整实现两种 Grammar；具体组合由真实内容池决定。
- Runtime 运行时 0 次 LLM 调用。
- 每个新编译 Run 都有声明式状态机；required Action 触发状态迁移。不得发布只有“第一步/第二步/第三步”的线性任务表。

## 7. 状态语义

- View：打开详情。
- Session Created：点击开始并创建记录，不计 Started。
- Started：第一次有效组件交互，每个 Session 只计一次。
- Completed：后端确认 Schema 完成条件满足。
- Result：由 Schema 与 Progress 计算。
- 不支持 Outcome Confirmed；Completed 不能表述为现实问题已经解决。

## 8. Source-bound 规则

每个 check、task、choice 必须包含可验证的 Source Anchor。Anchor 至少校验 blockId、quote、块内 offset 与 block hash。Bounded Source Excerpt 还必须显示精确覆盖范围；搜索摘要、模型补写和无法定位的内容不得进入 Published Run。

## 9. P1

- 知乎 OAuth 与跨设备身份。
- 更多 Published Run。
- 离线 Generic LLM Baseline 报告。
- 可选现场编译证明。
- 原文变化检测与重新编译提示。

## 10. 明确不做

公开编译页、完整 Admin UI、正文粘贴/文件上传/任意链接导入、无边界 Chat、Action Agent、社交评论、复杂推荐、排行榜、游戏化、模型控制运行路径、任意代码执行、企业级基础设施。

## 11. 成功定义

评委在 20 秒内理解用户价值，并能在 3 分钟内完成一个真实 Hero：操作使状态或路径发生变化、看到原文依据、得到结果、刷新后状态仍在。即使 LLM 暂时不可用，已发布 Hero 仍可完整运行。
